Part 4: DTO (Data Transfer Object)

이번 파트에서는 데이터를 안전하게 운반하는 DTO 클래스를 만듭니다. 요청(Request)용 5개와 응답(Response)용 4개, 총 9개입니다.

DTO(Data Transfer Object)란?
데이터를 한 곳에서 다른 곳으로 안전하게 운반하는 "택배 상자"입니다.

Entity vs DTO 차이:
Entity = DB 테이블과 직접 매핑되는 핵심 객체 (금고 속 원본 서류 — 함부로 수정하면 안 됨)
DTO = 데이터를 운반만 하는 일회용 상자 (복사한 서류봉투 — 자유롭게 사용 가능)

비유: "주문서 양식" — 고객이 주문할 때 정해진 양식에 맞게 작성해야 하듯이, 사용자의 입력도 정해진 형식(DTO)에 맞게 전달됩니다.

Step 11. Request DTO — 요청 데이터 전달 객체 (5개)

사용자가 브라우저에서 입력한 데이터를 서버로 전달할 때 사용하는 DTO입니다. @NotBlank, @Email, @Size 등의 검증 어노테이션으로 입력값을 자동 검증합니다.

검증(Validation) 어노테이션 정리

@NotBlank — 빈 문자열(""), 공백만(" "), null 모두 거부 (String 전용)
@NotNull — null만 거부 (모든 타입에 사용 가능, enum/숫자에 적합)
@Email — 이메일 형식(xxx@xxx.xxx) 검증
@Size(min=4, max=20) — 문자열 길이 제한
@Min(1) / @Max(5) — 숫자 최소/최대값 제한

Controller에서 @Valid와 함께 사용하면 자동으로 검증됩니다. 검증 실패 시 message에 적힌 에러 메시지가 반환됩니다.

11-1. LoginForm — 로그인 요청 DTO

src/main/java/com/example/mymatzip/dto/LoginForm.java
로그인 시 이메일과 비밀번호를 담는 DTO
LoginForm.javaJava
package com.example.mymatzip.dto; import jakarta.validation.constraints.Email; import jakarta.validation.constraints.NotBlank; import lombok.Getter; import lombok.Setter; @Getter // 모든 필드의 getter 자동 생성 (getEmail(), getPassword()) @Setter // 모든 필드의 setter 자동 생성 — JSON → 객체 변환 시 필요 public class LoginForm { @NotBlank(message = "이메일을 입력해주세요.") @Email(message = "올바른 이메일 형식이 아닙니다.") private String email; @NotBlank(message = "비밀번호를 입력해주세요.") private String password; }
사용 흐름
1. 사용자가 로그인 폼에 이메일/비밀번호 입력
2. JavaScript의 fetch()가 JSON으로 서버에 전송: { "email": "hong@mail.com", "password": "1234" }
3. Spring이 JSON을 LoginForm 객체로 자동 변환 (@RequestBody)
4. @Valid로 검증 → 통과하면 MemberService.login()에 전달

package com.example.mymatzip.dto; import com.example.mymatzip.entity.Category; import jakarta.validation.constraints.NotBlank; import jakarta.validation.constraints.NotNull; import jakarta.validation.constraints.Size; import lombok.Getter; import lombok.Setter; @Getter @Setter public class RestaurantForm { @NotBlank(message = "맛집 이름을 입력해주세요.") @Size(max = 50, message = "맛집 이름은 50자 이내로 입력해주세요.") private String name; // enum이므로 @NotBlank 대신 @NotNull 사용 @NotNull(message = "카테고리를 선택해주세요.") private Category category; @NotBlank(message = "주소를 입력해주세요.") private String address; private String phone; // 선택 입력 (검증 없음) @Size(max = 500, message = "설명은 500자 이내로 입력해주세요.") private String description; // 선택 입력 (길이만 제한) private String imageUrl; // 대표 이미지 URL (선택 입력) }
@NotBlank vs @NotNull 차이
@NotBlank는 String(문자열) 전용이고, Category는 enum(열거형)이므로 @NotNull을 사용합니다.
phone과 description은 선택 입력이므로 검증 어노테이션이 없거나, 길이만 제한합니다.
ReviewForm.java — 리뷰 작성 요청 DTO (펼치기)
src/main/java/com/example/mymatzip/dto/ReviewForm.java
리뷰 작성 시 내용, 별점, 맛집 ID를 담는 DTO
ReviewForm.javaJava
package com.example.mymatzip.dto; import jakarta.validation.constraints.*; import lombok.Getter; import lombok.Setter; @Getter @Setter public class ReviewForm { @NotBlank(message = "리뷰 내용을 입력해주세요.") @Size(max = 1000, message = "리뷰는 1000자 이내로 입력해주세요.") private String content; @NotNull(message = "별점을 선택해주세요.") @Min(value = 1, message = "별점은 1점 이상이어야 합니다.") @Max(value = 5, message = "별점은 5점 이하여야 합니다.") private Integer rating; // Integer(대문자) — null 체크를 위해 @NotNull(message = "맛집 ID가 필요합니다.") private Long restaurantId; // Long(대문자) — null 체크를 위해 private String imageUrl; // 리뷰 이미지 URL (선택 입력) }
int vs Integer, long vs Long
int/long(기본형)은 null을 담을 수 없어서 @NotNull 검증이 불가능합니다.
Integer/Long(래퍼 클래스)은 null을 담을 수 있어 "값을 선택하지 않은 상태"를 표현 가능합니다.
→ Request DTO에서는 래퍼 클래스를 사용하고, Response DTO에서는 확정된 값이므로 기본형도 사용합니다.

Step 12. Response DTO — 응답 데이터 전달 객체 (4개)

서버가 클라이언트(브라우저)에게 데이터를 전달할 때 사용하는 DTO입니다. Entity를 직접 보내지 않고, 필요한 정보만 골라서 이 DTO에 담아 전달합니다.

왜 Entity를 직접 보내면 안 되나요?
1. 보안 문제: Entity에는 비밀번호 같은 민감한 정보가 포함될 수 있음
2. 순환 참조: Entity 간의 양방향 관계가 무한 루프를 발생시킬 수 있음
3. 불필요한 정보: 클라이언트에 필요 없는 내부 필드까지 노출됨

비유: "예쁘게 담은 접시" — 주방(DB)에서 만든 음식(Entity)을 그릇째 내보내지 않고, 예쁜 접시(DTO)에 옮겨 담아 서빙하는 것입니다.

12-1. RestaurantResponse — 맛집 응답 DTO

src/main/java/com/example/mymatzip/dto/RestaurantResponse.java
맛집 정보를 클라이언트에 전달하는 응답용 DTO
RestaurantResponse.javaJava
package com.example.mymatzip.dto; import com.example.mymatzip.entity.Category; import com.example.mymatzip.entity.Restaurant; import lombok.Builder; import lombok.Getter; import java.time.LocalDateTime; @Getter // getter만 있고 @Setter가 없음! (응답 객체는 읽기 전용) @Builder // 빌더 패턴으로 객체를 조립하여 생성 public class RestaurantResponse { private Long id; // 맛집 고유 번호 private String name; // 맛집 이름 private Category category; // 카테고리 enum private String categoryDisplayName; // 카테고리 한글 이름 ("한식") private String address; // 주소 private String phone; // 전화번호 private String description; // 설명 private String memberNickname; // 등록자 닉네임 private Double averageRating; // 평균 별점 private LocalDateTime createdAt; // 등록일시 private String imageUrl; // 대표 이미지 URL // ── Entity → Response DTO 변환 (정적 팩토리 메서드) ── public static RestaurantResponse from(Restaurant restaurant, Double averageRating) { return RestaurantResponse.builder() .id(restaurant.getId()) .name(restaurant.getName()) .category(restaurant.getCategory()) .categoryDisplayName(restaurant.getCategory().getDisplayName()) .address(restaurant.getAddress()) .phone(restaurant.getPhone()) .description(restaurant.getDescription()) .memberNickname(restaurant.getMember().getNickname()) .averageRating(averageRating != null ? Math.round(averageRating * 10) / 10.0 : 0.0) .createdAt(restaurant.getCreatedAt()) .imageUrl(restaurant.getImageUrl()) .build(); } }
@Builder 패턴이란?
필드가 많을 때 생성자 대신 .builder().필드(값).필드(값).build()로 객체를 생성하는 방법입니다.

비유: 햄버거를 주문할 때 "빵 + 패티 + 치즈 + 양상추" 하나씩 골라 조립하는 방식입니다.
어떤 필드에 어떤 값을 넣는지 코드만 봐도 명확하게 알 수 있습니다.
from() 정적 팩토리 메서드
static 메서드이므로 객체를 만들기 전에 호출할 수 있습니다.
RestaurantResponse.from(restaurant, avgRating) 형태로 사용합니다.

평균 별점 반올림 로직:
4.267 * 10 = 42.67 → Math.round(42.67) = 43 → 43 / 10.0 = 4.3
리뷰가 없으면(null) 0.0으로 설정합니다.

package com.example.mymatzip.dto; import lombok.Builder; import lombok.Getter; import org.springframework.data.domain.Page; import java.util.List; @Getter @Builder public class PageResponse<T> { private List<T> content; // 현재 페이지의 데이터 목록 private int page; // 현재 페이지 번호 (0부터 시작) private int size; // 한 페이지당 데이터 수 private long totalElements; // 전체 데이터 수 private int totalPages; // 전체 페이지 수 private boolean first; // 첫 번째 페이지인지 private boolean last; // 마지막 페이지인지 // ── Page → PageResponse 변환 ── public static <T> PageResponse<T> from(Page<?> page, List<T> content) { return PageResponse.<T>builder() .content(content) .page(page.getNumber()) .size(page.getSize()) .totalElements(page.getTotalElements()) .totalPages(page.getTotalPages()) .first(page.isFirst()) .last(page.isLast()) .build(); } }
제네릭(Generic) <T>란?
"어떤 타입이든 담을 수 있는 만능 상자"입니다.
T 자리에 RestaurantResponse를 넣으면 → PageResponse<RestaurantResponse>
T 자리에 ReviewResponse를 넣으면 → PageResponse<ReviewResponse>

비유: 택배 상자의 크기/형태는 같은데, 안에 넣는 물건(T)만 바뀌는 것입니다.
Request DTO vs Response DTO 비교

Request DTO (LoginForm, ReviewForm 등):
- @Getter + @Setter — 값을 넣고 꺼낼 수 있어야 함
- 검증 어노테이션 (@NotBlank, @Size 등) — 입력값 검증
- 방향: 브라우저 → 서버

Response DTO (RestaurantResponse, ReviewResponse 등):
- @Getter + @Builder — 읽기 전용 (@Setter 없음!)
- from() 정적 팩토리 메서드 — Entity → DTO 변환
- 방향: 서버 → 브라우저
